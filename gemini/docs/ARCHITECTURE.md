# Architecture

GeminiCode is a hard fork of VS Code that ships the Gemini CLI as its built-in coding agent. This page explains how the pieces fit and why. Measurements and protocol behaviour that the design relies on are in [FINDINGS.md](FINDINGS.md). Work that is still open is in [ROADMAP.md](ROADMAP.md).

## Decisions

- **Fork VS Code, don't extend it.** The product is a standalone, branded application. A fork owns the shell, branding, first-run experience and admin policy.
- **Don't reimplement the agent.** GeminiCode runs the official `gemini --acp` as a child process ("sidecar") and implements only the client side of the [Agent Client Protocol](https://agentclientprotocol.com) (ACP). Sign-in, licensing and model calls stay in the CLI. The Gemini API SDK was ruled out because it cannot use a Gemini Code Assist license.
- **Build it as a built-in extension.** Almost all fork code lives in `extensions/gemini/`. It ships inside the app, adds very little to upstream merges, and builds without recompiling the workbench. Code moves into the workbench only for things the extension API cannot do.

Upstream files are touched only where a fork must register itself or rebrand. Each such edit carries a `GEMINI-FORK` comment, and the patch series in `gemini/patches/` keeps every one, JSON and icons included (see [../README.md](../README.md#touching-upstream-files)). They are:

- `product.json` (names, icons, links, Open VSX gallery, the download page URL, onboarding themes, Gemini setting policies);
- the top-level `README.md`, `SECURITY.md` and `AGENTS.md`, which point at the fork's docs;
- the build lists that register the extension (`build/npm/dirs.ts`, `build/gulpfile.extensions.ts`, `build/lib/extensions.ts`, `build/filters.ts`, `build/hygiene.ts`, `.eslint-ignore`, `eslint.config.js`);
- branding: packaging metadata (`build/lib/electron.ts`, `build/win32/code.iss`, and the macOS, Linux, Windows and server files and icons under `resources/`; the Debian scripts never add Microsoft's apt repository), a rebuild of the dev app when its name or icons change (`build/lib/preLaunch.ts`), the `.dmg` volume name and background (`build/darwin/create-dmg.ts`, which reads `resources/darwin/dmg-background.tiff`), packaging without upstream's Copilot extension (`build/gulpfile.vscode.ts`), GeminiCode’s version in the About dialog and the Gemini CLI in use, asked of the extension through `_gemini.cliVersion` (`platform/dialogs/electron-browser/dialog.ts`, `workbench/electron-browser/parts/dialogs/dialog.contribution.ts`), and the workbench icons (`code-icon.svg`, `letterpress-*.svg`);
- system notifications and the Dock badge: `contrib/gemini/electron-browser/gemini.contribution.ts`, a fork-only file imported from `workbench.desktop.main.ts`, registers the internal commands `_gemini.showToast`, `_gemini.hideToast` and `_gemini.setApplicationBadge`, which the extension API has no equivalent for. When the workbench loads, it also registers the defaults that must hold from the first frame, before any extension runs (an extension's `configurationDefaults` arrive after the startup page has decided what to open): upstream's AI off, no onboarding, startup editor or empty-editor hint, the view icons at the top of the side bar, the secondary side bar hidden, pill tabs, and the browser button in the title bar. The same file loads the bundled code fonts (JetBrains Mono and Geist Mono, TTF files in `contrib/gemini/electron-browser/media/` declared in `geminiFonts.css`), because extensions cannot add fonts to the editor. It also loads `geminiSoft.css`, the half of GeminiCode Dark and Light a colour theme cannot express: a static graphite tint at the top of the window (no accent hue) behind the Modern UI layout's floating cards, 8px card corners whose top edge catches the light, the title bar's Home button, Agents | Editor switch (its lens slides by one transform) and tabs as glass (a translucent fill and a rim), and upstream's frosted pop-ups made opaque (no blur) with a sheen and the rim, all keyed to `gemini-soft`, a class the same file puts on each workbench window while one of the two themes is on (stylelint rejects matching on the theme's own class name). It is static, apart from the lens's one transform, so it costs nothing at runtime: profiled with an agent streaming a long reply while the chat scrolls, a menu open over it and a mode switch, three runs before and after, no measure (paint, raster, composite, layout, dropped frames) moved beyond the spread between runs, under 0.01 ms per frame. Its CSS variables are listed in `build/lib/stylelint/vscode-known-variables.json`, which hygiene checks against. Its siblings `geminiModes.ts` holds the window modes (below), `geminiTitleTabs.ts` Agents mode's title bar tabs (below), `geminiBrowser.ts` the agents' browser (below), and the i18n list in `build/lib/i18n.resources.json` names the folder;
- the native frame: Gemini first in the activity bar (its order in `api/browser/viewsExtensionPoint.ts`, plus a one-time move for profiles that cached it lower in `browser/parts/paneCompositeBar.ts`), **New Agent** in the macOS Dock menu (`platform/menubar/electron-main/menubar.ts`, run in the window last used), and a description on agent tabs for their line counts (`WebviewInput` in `webviewPanel/browser/webviewEditorInput.ts`, set through `_gemini.setAgentTabs`, matched by tab title). Agent tab icons show the agent's state as SVGs in `media/tabs/`, because tab labels draw a ThemeIcon without its colour or spin;
- slimming upstream down: with `chat.disableAIFeatures` on (GeminiCode's default), Copilot setup does not start (`chatSetupContributions.ts`), so there are no entitlement requests to GitHub at startup; `product.json` carries no Copilot auto-update, auth trust or voice endpoint; the `tunnel-forwarding` extension, which needs the `code` CLI GeminiCode does not ship, is left out of the build (`build/lib/extensions.ts`). Telemetry is already off, because `product.json` has no `enableTelemetry`. The layout also tolerates the activity bar being hidden before its grid exists (`browser/layout.ts`), which Agents mode does at startup;
- four workbench edits: Chat commands hidden from the Command Palette while upstream AI is off (`commandsQuickAccess.ts`), the Gemini extension cannot be disabled (`extensionEnablementService.ts`, with its test), the product name in the welcome walkthrough (`gettingStartedContent.ts`), and the default colour themes (`ThemeSettingDefaults` in `services/themes/common/workbenchThemeService.ts`, with a fallback to upstream's Dark/Light 2026 in `services/themes/browser/workbenchThemeService.ts` if the GeminiCode themes are ever missing). `product.json` lists the GeminiCode themes in `onboardingThemes` too.

## How a prompt flows

```
Chat webview ──postMessage──▶ ChatController ──▶ AgentClient ──▶ AgentRuntime ──stdio JSON-RPC──▶ gemini --acp
     ▲                              │                                  │
     └──── batched item updates ◀───┴── ChatTranscript ◀── session/update notifications
```

1. **The agent process.** `AgentSidecar` spawns the CLI with the application's own Node (`ELECTRON_RUN_AS_NODE=1`), so users need no Node install. The process inherits the editor's environment, including proxy and CA variables, with `GOOGLE_CLOUD_PROJECT` set to the resolved project (and `GOOGLE_CLOUD_PROJECT_ID` cleared), `GEMINI_CLI_NO_RELAUNCH=true` and an explicit heap size ([FINDINGS.md](FINDINGS.md#starting-the-agent)), plus `--admin-policy` and, only with `gemini.agents.allWorkspaceFolders` in a multi-root window, `--include-directories` for each folder (`includeDirectoryArgs`; ACP sessions build their config from the process's arguments, so every session's workspace would cover all the window's folders). Off by default, so an agent keeps to the folder it works in. With it on, a change to the folders restarts the process once no prompt runs. It restarts a crashed process with backoff (1 s, 4 s, 15 s; the count resets once a process stays up for a minute), but never after a fatal exit such as a failed sign-in (exit code 41). Exit code 199, the CLI asking to be relaunched, restarts it at once. The process starts when a chat first opens, not at activation, and changing a setting that affects it (CLI path or version, project, approval or shell settings) restarts it: at once when the change takes a permission away or changes which MCP servers may load (`takesAway`), otherwise once no prompt runs, so turning on YOLO doesn't cut off a running turn. Its command is worked out without blocking the extension host: the CLI's resolution, the CLI's settings and the admin policy file are read at once, asynchronously, and a stop that comes while they are read wins, so a stopped agent never starts late.
2. **One process, many agents.** `AgentRuntime` runs `initialize` once and serves every chat from that process; each chat is its own ACP session with its own `cwd`. With a Google sign-in a new session takes about 0.8 s, against about 3 s for a new process ([FINDINGS.md](FINDINGS.md#sessions)). `AgentWarmup` starts the process 3 s after the window opens (`gemini.agent.startEarly`), but only when it can start without asking anything: setup finished before, a saved sign-in or API key, and no project problem, since a CLI with no saved sign-in opens the sign-in flow as it starts. While the user types on Agent Home, `AgentRuntime.prepareSession` opens a spare session for that folder and the agent's browser servers (the agent id is chosen ahead for that), which the next `newSession` with the same key takes, so starting the agent waits for no `session/new`. A project's coordinator and threads never take a spare, because their sessions need the project's MCP server, which a spare opens without.
3. **Sessions.** `AgentClient` opens a session (`session/new`, or `session/load` to resume), signs in when the CLI asks, sends prompts, and exposes the modes and models the agent reports, minus any mode the admin policy turns off. Nothing in the UI hardcodes a mode or model ID. It closes the sessions it leaves (the one a new session replaces, its own when disposed, and one an outdated open created) when the CLI advertises `sessionCapabilities.close`; gemini-cli 0.64.0 does not, so they stay until the process exits. The model picker rebuilds the list the terminal's `/model` dialog shows from the one the CLI sends apps, which can name a model twice and lacks Gemma (`modelList.ts`). The model the user picked last (kept in global state) is applied to each new or reopened session when the agent offers it; with no pick yet, or one the agent no longer offers, it is the first Flash model the agent lists (`defaultModel`, never Flash-Lite). That also spares the CLI its Auto routing call ([FINDINGS.md](FINDINGS.md#a-prompts-first-reply)).
A chat restored at launch (`openLater`) waits to `session/load` until its tab is shown or used, or 2 s after its webview is ready, so restoring many tabs does not replay every history at once.
4. **Rendering.** `sessionUpdates.ts` turns `session/update` notifications into a few UI events, and `ChatTranscript` folds them into plain, serialisable items. The controller streams item changes to the webview about 30 times a second, sending only appended text for streaming messages. A long transcript shows its last 30 items first and adds the older ones above them in idle time, 20 at a time; all but the last 30 elements are marked settled, so they skip layout while out of view. An agent's chat whose tab or pane is hidden keeps the updates it receives and renders them, coalesced, when it shows again (the host sends `visibility`, since `document.hidden` doesn't see a hidden tab). A streaming reply re-renders only its unfinished tail; a tail over 4,000 characters re-renders at most every 150 ms, and code in an unclosed fence isn't highlighted until it closes. The webview renders agent Markdown with raw HTML disabled, then adds GitHub-style callouts (`> [!NOTE]`), scrolling tables and links on file names in `code` (`markdownExtras.ts`; the extension finds the file from the agent's folder, else by name). Math (`$...$`, `$$...$$`, `\(...\)`, `\[...\]`) is left as placeholders (`mathRule.ts`) and typeset by KaTeX, a bundle of its own that loads with the first reply that has math (`math.ts`, `katex.ts`); prices and shell variables stay text.
5. **Code blocks.** Finished code blocks are highlighted by highlight.js (about 30 languages, `webview-src/highlight.ts`), a bundle of its own that loads with the first code block and runs when the view is idle; results are cached, so a re-render is coloured at once. A block still streaming stays plain. The colours are the colour theme's own: `themeTokens.ts` reads the active theme's file (and those it includes) and matches its TextMate rules to about 20 categories (`tokenColors.ts`), so code in chat looks as it does in the editor. Themes that can't be read fall back to Dark Modern and Light Modern colours.
6. **Permissions.** `PermissionBroker` holds each `session/request_permission` until the user picks one of the options the agent sent. A request that proposes an edit opens a real diff editor. Stopping a turn answers any open request as cancelled. The CLI accepts "Allow for this session" on a shell command that reuses earlier tool output but doesn't keep it ([FINDINGS.md](FINDINGS.md#approval-modes-and-the-clis-own-changes)), so GeminiCode keeps those approvals itself, per session and in memory (`sessionApprovals.ts`): the programs allowed are answered on repeats, except commands that reach the network, write through a redirection or run code they build. The command is read from the call's `rawInput`, not its title. Programs that run another program (`env`, `xargs`, `sudo`, `timeout`, shells, interpreters such as `python` or `node`, `npx`), a program run by relative path, an environment prefix other than locale and colour variables, and arguments that run code (`find -exec` or `-delete`, `awk` with `system(` or a pipe, `git -c`) always ask again. Approvals of task runners (`npm`, `make`, `gradle`, `cargo`, `go` and the like) lapse when the agent writes a build file through the editor (`package.json`, a `Makefile`, `build.gradle`, `Cargo.toml` and so on), since the next run would run what the agent wrote. In YOLO the chat allows requests itself, except the confirm class (Team tools, below), which always asks. **Commands Allowed for This Session...** lists and forgets them.
7. **Files.** The agent's `fs/read_text_file` and `fs/write_text_file` requests go through the editor. Reads see unsaved changes. Writes are applied as a `WorkspaceEdit`, so they can be undone, and then saved, because the CLI's own shell and search tools read the disk. Requests are limited to the agent's folder, skip git-ignored files for reads, and refuse secret files: `.env`, private keys and credential files, cloud credentials (`application_default_credentials.json`, service account keys, the `gcloud` folder) and cluster and registry configs (`.kube`, `kubeconfig`, `.docker`, `.dockercfg`, `.vault-token`). A symbolic link is followed: its real target must be inside the folder too, and is checked for secrets again, so a link to `~/.aws/credentials` or to `.env` is refused. Git-ignore checks go to one long-lived `git check-ignore --stdin` per folder (`gitIgnore.ts`) rather than a process per read, with answers cached for 30 seconds.

## The agent workspace

- **Agents and Editor modes.** `contrib/gemini/electron-browser/geminiModes.ts` (fork-only) switches the window between two layouts from a switch in the title bar or ⌥⌘M. Agents mode hides the activity bar (by setting `workbench.activityBar.location` to `hidden` in memory only, so the user's own setting returns in Editor mode), shows the Gemini side bar on the left and the extension's **Changes** panel in the secondary side bar; Editor mode is the classic layout. Agents mode's views are fixed: when the user opens any other view container in the side bar (a command, a shortcut or an extension revealing it), the window switches to Editor mode with that container open and says so once. Each mode stores which parts were open, per workspace (Editor mode also which side bar and secondary side bar), and switching only shows and hides parts. The mode is the context key `gemini.mode`, which the extension's views use in their `when` clauses, and the workbench tells the extension about changes through `_gemini.modeChanged` (`_gemini.getMode` answers at start). The same file draws a pill in Editor mode's title bar for each agent that is working, waiting or done and unread, from what the extension sends with `_gemini.setAgentStatus`; clicking one opens that agent. In Agents mode the pills are dropped, because the title bar tabs and the agent list already show each agent's state. In Agents mode the group holding the agents has no tab row of its own: `browser/parts/editor/geminiTabRows.ts` (fork-only) takes a policy from `geminiModes.ts`, and a marked edit in `editorTitleControl.ts` gives that group no tab row while every other group keeps the normal one (Agents mode sets `workbench.editor.showTabs` to `multiple` in memory only), so a file an agent opens has its name, × and editor actions. The agents' tabs go to `geminiTitleTabs.ts`: a fork-only tab strip in the title bar, one capsule of tabs mirroring the agents' group (icon and agent state, truncated title, close button, dirty dot, click to activate, middle-click to close, context menu, overflow scroll), which stays on the agents when a file beside them is clicked. It redraws only on that group's own model events. Each agent's files get a side group of their own, from `geminiAgentGroups.ts` (fork-only): the extension asks for the agent's column with `_gemini.agentGroupColumn` before it opens a file, diff or the Changes view, and the group is made beside the agents' group the first time. Only the group of the agent in front is visible; the others are hidden with the grid's own view visibility, through `geminiSetGroupVisible`, a marked addition to `editorPart.ts`, so switching agents reloads nothing and each agent's files come back as left. A group that comes to hold an agent or Agent Home is the agents' group from then on and is never hidden (a hidden group's webviews lose their CSS anchor and draw as a small box in the corner), and new agents and Agent Home open in the agents' group (`_gemini.agentsColumn`), not the active group. Activating a hidden group (from Open Editors, say) brings its agent to the front. Closing an agent's tab or removing the agent sends `_gemini.closeAgentGroup`, which closes its files except those with unsaved changes; the group goes when its last file closes. The agent-to-group map is kept in workspace storage, since group ids survive a reload. The title bar also carries a search button in Agents mode, which opens Quick Open in place of the Command Center that `geminiModes.css` hides there, and the integrated browser button, which the window defaults turn on (`workbench.browser.showInTitleBar`). The foot of Agents mode's side bar shows the selected agent's branch, which the extension sends with `_gemini.setAgentFooter` (a tree view cannot draw a footer). A new workspace opens in Agents mode. The Changes panel is contributed by the extension and can register after the layout is applied (or not at all on a first open in Restricted Mode, where the extension does not run), so Agents mode opens it as soon as it registers, remembering in workspace storage that it still owes it. At startup it also fills an open but empty secondary side bar with Changes; a view the user put there is left alone.
- **Spell check in the composers.** `windows.ts` leaves Electron's spell checker on (a marked one-line edit), and `geminiSpellCheck.ts` (fork-only, registered with a marked line in `windowImpl.ts`) shows the system's suggestions, Add to Dictionary, and Cut, Copy and Paste when a right-click in an editable field reaches the window. Upstream's inputs and editors set `spellcheck="false"` on themselves; the Gemini pages set it off on their body and on for the chat and Agent Home composers, which let their right-click through instead of the webview host's menu. `gemini.chat.spellCheck` turns it off live. Languages follow the OS.
- **Folded turns.** `webview-src/workFold.ts` (no DOM, unit-tested) splits a turn's items into the fold (thoughts, tool calls, what the agent said between steps, answered questions) and what shows after it (the answer, the plan, notices, a waiting question, the turn's end), groups runs of tool calls of one kind, and counts what the turn did; `work.ts` draws the fold's line, the pinned changed files and failures, and run lines; `transcript.ts` lays a turn out again when a new item or a step's change arrives, moving items' elements rather than rebuilding them. A folded fold holds no elements for its steps, and an unchanged fold or run line is kept, so a long turn streams no slower than the flat view. `gemini.chat.foldFinishedWork` turns it off live.
- **Themed menus.** Upstream defaults `window.menuStyle` to `native` on a stable Mac build, which opens every workbench menu (the browser's Add to Gemini chevron, right-clicks in the editor, the explorer and tabs, select boxes) as the system's menu. `contrib/gemini/electron-browser/geminiContextMenu.ts` (fork-only) registers `custom` as the default, so they are drawn in the theme's `menu.*` colours; a user's own setting still wins, and the macOS menu bar stays the system's. Two menus are built in the main process: a right-click in a page of the built-in browser (`browserViewMainService.ts`, a marked edit) and the composers' spelling menu (`geminiSpellCheck.ts`). Both go through `platform/windows/electron-main/geminiContextMenu.ts` (fork-only), which sends the items to the window over `vscode:geminiShowContextMenu`; the workbench shows them with its context menu service and answers with the item picked, which main then runs. With `window.menuStyle` set to `native` the workbench answers at once and main opens the system's menu as before. A page in a window of its own (not a workbench window) keeps the system's menu. An HTML `<select>` opens the system's menu whatever `window.menuStyle` says, so none is shown: in a webview each is wrapped by `webview-src/selectMenu.ts`, which keeps it hidden as the value and draws a button and one of our menus (`menu.ts`) in its place; the New agent popup (`geminiNewAgentDialog.ts`) uses the workbench's `SelectBox`, custom-drawn unless `window.menuStyle` is `native`. `test/webview/themedMenus.test.ts` fails on a new bare `<select>` in either place. The popup's model list comes from a running agent or, with none, the last list any session sent (`knownModelList`, kept in global state).
- **Projects (preview, `gemini.projects.enabled`).** A project is a coordinator agent whose chat is the project chat, plus threads, each an agent on a new branch in its own worktree (`src/host/projects.ts`). What the user writes in the project chat goes to a `ProjectHub` (`src/acp/projectHub.ts`), which wakes the coordinator with the threads' state, open Conductor tracks (`conductor.ts`) and the new events in one prompt, and batches events while it is mid-turn. The coordinator runs on a named Flash model and reaches the hub through the `geminicode-project` MCP server (`projectMcp.ts`, 127.0.0.1 with a token per caller): `start_thread`, `message_thread`, `list_threads`, `read_thread` and `post`; a thread has `report`. A reply that only repeats the coordinator's last `post` is dropped (`ChatTranscript`), since models often end the turn by saying the post again. Its calls of those tools are allowed at once and hidden, and any other tool it asks for is refused. Threads show as cards in the project chat that update in place, with Merge back, Review changes, Undo thread and Approve plan; approvals stay in the thread that asked. "New thread" in the + menu opens a dialog (title, brief, branch, model, Plan first) in the chat's webview; the thread starts at once and the coordinator hears afterwards. `start_thread` returns as soon as the worktree exists: worktrees are added one at a time per repository, so threads started together can't pick the same branch name, and the repository's setup script runs behind a notification while the thread's agent starts. The brief is sent when setup ends, and a note sent to a thread that is still setting up or mid-turn waits for that, rather than being dropped. A thread that fails to start removes its worktree and branch again. The coordinator's session runs in an empty folder of its own (`~/.geminicode/projects/<id>`), so it has no code to read and hands work to threads. The Gemini CLI loads MCP servers only in trusted folders, so opening or starting a project asks to trust the coordinators' folder and the repository's worktrees folder when they aren't (`trustedFolders.ts`), then waits for the agent's restart. Agent Home lists projects apart from agents. The coordinator's folder links to the repository's context files (GEMINI.md, AGENTS.md and any `context.fileName`) but not its `.gemini` or `.agents` folders, whose skills, commands and MCP servers would pull it into doing the work; a thread's worktree links whatever rules the repository ignores (`projectRules.ts`). A follow-up on a thread's work goes to that thread whatever its state; once merged, a thread is resolved (kept on its record, so across reloads) and takes nothing more unless the user asks to reopen it. Opening a project starts only its six most recently used open threads' sessions without tabs (`warmThreads`, `resumeThread`), one at a time and 1.5 s apart so they don't compete with the window's start, skipping any whose worktree is gone; see "Projects with many threads". Removing a thread from the agent list, or with its branch after a merge, also removes it from the hub and marks its card removed. Merge back checks the thread is idle both before and after its dialog, and runs once per thread at a time. Only the user's messages wake the coordinator: a thread's result, question or failure is the user's to take up in that thread, and reaches the coordinator as context with the next message. A thread's chat has a bar back to its project chat, and the project chat's side panel lists every thread to open. New Project otherwise asks only which folder (an open workspace or any Git folder) and opens the project chat at once, named after its repository. The agent list has a Projects section (projects with their threads below) above the Agents section, each with its own + and a note when empty; Agents mode shows both, since its list has no header (`geminiModes.css`). A side panel (`webview-src/project.ts`) lists the threads by state (each opens its chat), the Conductor tracks and the coordinator's model when the view is at least 1000 px wide, and resizes from a sash (drag, arrow keys, double-click to reset); the extension sends it only after a burst of card updates settles. The go/no-go numbers are in `FINDINGS.md`.
- **Project settings and memory.** Project settings opens as a popup over the project chat (`webview-src/projectSettings.ts`, its state in `settingsLogic.ts`) from the side panel's gear or the project's context menu, with General (name, repositories, defaults for new threads, stats) and Memory (the Memory text, context files and which role reads each, the repositories' own rules files, and a token estimate) tabs; nothing is saved until Save, Cancel and Escape ask before discarding edits, and refreshes from the extension keep unsaved edits. Settings live in the project's own folder, never in a repository (`projectStore.ts`): `project.json`, `instructions.md` and `memory/*.md`. The Gemini CLI imports `@` files only from inside a session's folder, so memory is not passed as rules files: the coordinator gets it in a wake's `<notes>`, sent again only when it changes; a single-repository thread gets it as unseen context ahead of its brief (`ChatController.addContext`); a multi-repository thread gets it in its folder's `GEMINI.md`. A new project's Memory text is Gemini's draft (`projectDraft.ts`): one direct request on the quick-edit model with each repository's README, agent rules, manifest and top folders, saved with the time it was drafted so the popup asks the user to review it until they save from the Memory tab. Adding a repository redrafts a text that is empty or still unreviewed.
- **A project's tools, checked.** A coordinator whose session opened before the CLI trusted the project's folders has no `start_thread` and can only say so. So before the first wake goes out, `Projects.ensureTools` opens the session and waits up to 10 s for the CLI to list the coordinator's tools (`ProjectMcpServer.whenListed`); if it doesn't, the message waits while GeminiCode asks to trust the folders, or, when they are trusted already, restarts the agent once no agent is working (`reloadProjectTools`), and the session reopens with them. When something else keeps the tools out, `projectToolsCheck.ts` reads the files the CLI decides by (folder trust, `mcp.excluded`, `admin.mcp.enabled`, `mcp-server-enablement.json`) and the project chat names the cause instead of restarting.
- **A project's repositories in the footer.** In a project with several repositories, the coordinator's chat shows one pill per repository with its checked-out branch where the folder and branch pills go, and a thread across repositories shows its worktree of each (`ViewGit.repos`). Each pill opens Copy Path and Reveal for that repository.
- **Focus.** Switching to an agent's or thread's tab sends its chat `focus`, and showing Agent Home sends Home `focus`: the message box takes the cursor, unless a popup such as Project settings is open.
- **Projects with many threads.** Opening a project costs the same with 5 threads or 500. Only the six most recently used open threads start with it; any other starts when it is likely needed: the pointer rests on its card or side-panel row, or the keyboard selects it in the agent list (`onIntent`, `prepareThread`), when it is opened, or when the coordinator messages it. A thread started that way shows its saved chat first, and prompts wait until that chat is in (`ChatController.holdPrompts`), so a note can't replace the history. `read_thread` reads a thread that isn't running from its saved chat rather than starting it. Each wake lists every open thread but only the ten latest merged ones (`wakeThreadLines`); `list_threads` with `all: true` lists the rest. A thread merged over a week ago is archived (`isArchived`, from `resolvedAt`): it moves under an Archived row in the agent list and leaves the side panel, and keeps its record, chat and branch. Project settings' Clean Up removes merged threads' worktree folders whose work is all merged into the repository's checked-out branch (nothing uncommitted, no commits ahead), after a dialog that gives the space freed; opening or messaging such a thread puts its folder back from its branch first (`restoreWorktree`). `test/perf/budgets.test.ts` times a 500-thread project.
- **Projects across several repositories.** A project lists its repositories in `project.json`, its own repository first, each with a key (its folder's name). With more than one, the coordinator's first wake adds how to choose them and every wake lists them as `<repositories>`; `start_thread` must name the thread's `repos`, and errors otherwise, telling the coordinator to ask the user which when the request doesn't say. One thread holds every repository a task touches: its agent runs in its own folder, `~/.geminicode/threads/<project>/<branch>`, which holds a worktree of each repository (`<key>/`, all on one branch free in every repository) and a generated `GEMINI.md` (which folder is which, that the folder isn't a repository, and the memory) and `.geminiignore`. That folder needs trusting too, so a project with several repositories also asks to trust `~/.geminicode/threads`. A thread that needs another repository calls `add_repo`, which only multi-repository threads are offered. Each repository merges back on its own from the thread's card (or a pick in Merge back), committing only that worktree's work; the thread is resolved once no repository has work left. Undo and Remove delete every worktree, then the thread's folder. The New thread dialog offers the repositories as checkboxes, and takes its model, Plan first and branch prefix from the project's defaults.
- **Agent Home** (`agentHome.ts`, `webview-src/home.ts`). In Agents mode it opens whenever the editor area is empty (except right after closing Agent Home itself), and from the house at the start of the title bar (`geminiModes.ts`, which runs `gemini.home`). Its composer starts an agent in a chosen workspace and sends the prompt in one step, optionally on its own branch named after the prompt; cards show the agents that are working, waiting, done or have changes, with Stop, Review, Merge Back and Open; earlier agents can be resumed. The page loads only when first shown.
- **Undo and Rewind** (`checkpoints.ts`, `checkpointStore.ts`). After each turn, the text every file had before the agent first edited it in that turn is kept, for the last 100 turns and 20 MB per agent, and saved to `<globalStorage>/checkpoints/<agent>.json` after the turn ends, never while a tool runs; it is deleted with the agent. ACP has no rewind, so Rewind appends the record the CLI's own `/rewind` writes (`{"$rewindTo": <message id>}`, `rewindCliSession` in `cliSessions.ts`) to the session's `.jsonl`, then loads the session again over ACP in the same process; the CLI rebuilds its history without that message and what followed. Rewind always does both: it undoes the code from the first kept turn after the message, then rewinds the session. The message is found by its text; if it can't be (a team command's prompt), only the code can be undone. `realRewind.test.ts` checks this against the real CLI.
- **Subagents.** The CLI's `invoke_agent` tool reaches ACP as one `think` tool call titled `Delegating to agent '<name>'` and its final report. The chat draws it as a Subagent row (`subagentName` in `webview-src/chatLogic.ts`); any other title falls back to a plain tool row. The subagent's own steps are not sent over ACP.
- **Changes panel** (`changesPanel.ts`, `webview-src/changes.ts`). Agents mode's live diff of what the agent in front changed: each change as a unified diff with Keep and Undo, which run the same commands as the editor's CodeLenses, plus Keep All, Undo All and Commit (or Merge Back for an agent on its own branch). Diffs are worked out with `lineDiff.ts` against the open document's text, 150 ms after the last edit, and only while the panel is visible. In Editor mode the Changes view below the Agents pane is shown instead.

- **Agents pane.** A tree of workspaces (the open folder plus any you add) with agents under each. Workspace rows show just the folder's name (its path is the tooltip). Each agent row shows its status as a coloured dot, or a spinner while it works (working, waiting for permission, done but unread, needs attention, idle, or not started in this window), and one short note after the title (`src/acp/agentRow.ts`): the turn's clock while it works (ticked once a second for just the working rows, and only while the pane is visible), "waiting" when it needs permission, the lines it added when it is done, otherwise how long ago it was active. The `+N −M` count and the git branch (read from `.git/HEAD`) are in the tooltip. An agent takes its name from its first prompt unless the user renames it. Removing an agent deletes its saved conversation; removing a workspace only drops it from the list.
- **Agent tabs.** Each agent opens as an editor tab that reuses the chat webview, and is the main editor. Files, proposed edits and diffs that the agent's chat or its Changes open go in the agent's own side group (above); outside GeminiCode's workbench, in the group after the agent's tab, added once if there is none (`editorPlacement.ts`). Either way the chat stays in view. Add to Chat and the chat commands act on the agent tab in front, else the running agent used last, else a new agent (`AgentsView.chatFor`); there is no sidebar chat.
- **Changes view.** This view sits below the Agents pane in the Gemini side bar and lists the files the agent in front has edited, recorded from its completed edit tool calls. Each file opens a diff against its text from before the agent's first edit, **Open All Changes** shows them in the multi-diff editor, and **Clear List** forgets them.
- **Git.** Each chat's composer shows the folder's branch as a pill that switches or creates a branch, through the built-in Git extension, which is only activated when the user picks an action (`gitActions.ts`). An agent's chat also offers **Create Branch & Commit**, which stages and commits only that agent's changed files to a new branch (suggested as `gemini/<agent name>`, with the agent's name as the message), warns first when other files are already staged, and then clears the agent's Changes list.
- **Worktrees.** An agent can work on its own branch in a Git worktree (`src/acp/worktrees.ts`, plain `git` commands). The worktrees live in `~/.geminicode/worktrees/<repository>/<branch>` instead of inside the repository, so the open workspace's search, file watchers and language servers don't see every file twice. The agent's session gets the worktree (or the workspace's matching subfolder in it) as its `cwd`; the agent record keeps the folder, branch and base. **Merge Back** commits leftovers with the agent's name and runs `git merge --no-ff` in the workspace's repository, leaving conflicts for Source Control. Creating one costs a checkout of the repository's files, shown as progress, and nothing on later prompts.
- **Long chats.** The chat draws a tick per prompt down its right edge (`webview-src/promptNav.ts`) and jumps between prompts with ⌥⌘↑ / ⌥⌘↓; prompt positions are read only on a jump, or once a frame while scrolling, to light the current tick. **Open Chat as Markdown** turns the transcript items into one untitled Markdown document (`src/acp/chatMarkdown.ts`): prompts and replies under headings, thoughts folded, tool calls as a list; an agent that is not running in the window is read from its saved conversation.
- **Follow the agent.** With the composer's eye on, the chat opens the file of each read tool call as soon as the call names it, and of each edit or move once it completes, at the call's line (`src/acp/follow.ts`). Each call opens at most once, at most one file every 250 ms (the latest wins, so a burst of reads does not flicker), as a preview with focus left in the chat, in the agent's editor group. Folders, missing files, files outside the agent's folder and files `secretPathReason` (`fileAccess.ts`) flags, such as `.env` or anything under `.ssh`, are skipped; searches, commands and fetches open nothing.
- **The GeminiCode browser.** Upstream's Integrated Browser ships with agent tools, but they reach only Copilot's chat. GeminiCode serves its own: `src/acp/browserMcp.ts` is an MCP server (Streamable HTTP with plain JSON replies) on 127.0.0.1, with one path and its own bearer token (an HMAC of a random key) per agent; `src/host/browserTools.ts` passes it to each agent session in ACP's `mcpServers`, only when the CLI advertises `mcpCapabilities.http` (the bundled CLI does), and disposes the server when `gemini.browser.enabled` is turned off. Its tools (`browser_navigate`, `_snapshot`, `_click`, `_hover`, `_type`, `_select`, `_press_key`, `_scroll`, `_back`, `_forward`, `_reload`, `_wait`, `_screenshot`, `_dialog`, `_console`, `_network`, `_dev_servers`) call the fork-only workbench commands in `contrib/gemini/electron-browser/geminiBrowser.ts`, which use upstream's browser view and Playwright services directly: each agent has a Playwright session `gemini-agent:<id>` and owns the pages it opens, and the commands run only fixed actions, never code from the extension. That file also adds the "Gemini is using this page" bar with Stop to pages an agent owns. Pages open in the side group without taking focus, and open, snapshot and screenshot return the page's real URL, which the server checks after every step. Local http(s) URLs open freely and `file:` URLs follow the agent's file policy; any other origin, including one a click or redirect leads to, asks once per agent and site (a modal dialog), and the page goes back if refused; `gemini.browser.allowOtherSites` off refuses them all. Removing an agent closes its pages and session, except pages the user handed it, which go back to the user. **Let Gemini Use This Page** (an `Action2` in `geminiBrowser.ts`, in the page's actions toolbar and the Command Palette, hidden on any agent's page through the editor-scoped `geminiBrowserPageIsAgents` key and when `config.gemini.browser.enabled` is off) calls the extension's `_gemini.browser.handOver`, which always shows a quick pick first: New Agent..., the running agents, and up to ten recent ones, which start before they get the page (`BrowserTools.handOver`; New Agent opens one popup, `_gemini.newAgentDialog` in `geminiNewAgentDialog.ts`, for the folder, its own branch or not, the model, the mode and an optional task; the workbench draws it because no extension API can float a form over the browser's page, and its block carries `monaco-dialog-modal-block` so the browser's overlay manager hides the page under it. `AgentsView.newAgentFor` then starts the agent with its tab open, and a task is sent with the page), checks the page's URL as for the agent's own pages without asking (`handOverRefusal`: http(s) unless the policy keeps agents local, `file:` per the file policy, nothing else), then calls `_gemini.browser.share`: the workbench refuses a page that any agent owns or is being handed over (one agent per page), adds the agent's session as the page's audience (the main process refuses that outside the network policy), makes the agent the owner, and waits for Playwright to see it. The extension checks the returned URL again, records the page as the agent's and its origin as allowed for that agent (`adopt`), and adds a note to the agent's composer that names the page and says its text is not the user's. **Stop Sharing** on the bar (`gemini.browser.stopSharingPage`) sets the owner back to the user and removes the audience; the agent's next tool call finds no page. A page counts as handed over when it is recorded as such or is not in agent storage (pages agents open always are), so a window reload doesn't make Remove Agent close it. The extension also defaults `workbench.browser.openLocalhostLinks` on.

The tool descriptions, the server's `instructions` and the shared-page note tell the model to use the browser rather than the CLI's `web_fetch` for local, private-network and signed-in pages: gemini-cli's web fetch refuses any host that resolves to a private address (or doesn't resolve) before fetching, and otherwise fetches through Google. When a `web_fetch` call fails that way (`src/acp/webFetchHint.ts`), the chat adds a notice pointing to the browser. `browser_console` reads the page's console from the browser view (`getConsoleLogs`); `browser_network` reads requests that a fixed Playwright listener (`recordNetwork` in `geminiBrowser.ts`, attached when the agent's page opens or is handed over, the newest 500) keeps on the page; both filter in the extension and send back a count and the last lines, never the whole log. `browser_dialog` uses Playwright's `replyToDialog`. `browser_dev_servers` (`src/acp/devServers.ts`) sends one HTTP request to each usual dev port on `127.0.0.1` and `::1` at once, only when called. `gemini.browser.allowedOrigins` (`isAllowedOrigin`) is checked before anything else for every http(s) page, on navigate, after every step and on hand-over. With `gemini.browser.keepSignIns` on, `_gemini.browser.open` creates agents' pages in workspace storage instead of agent storage (`agentPageStorage`), except where the user's own pages use workspace storage, in an empty or untrusted window, or under a network policy; the ids of pages agents opened are kept in workspace storage, so a page is still told apart from one the user handed over after a reload.

**Add to Gemini** (the `GeminiBrowserAddToGemini` split button in a page's toolbar, `GeminiPageContext` in `geminiBrowser.ts`) does for Gemini what upstream's Add to Chat does for Copilot's chat, which GeminiCode turns off: it drives the same page overlays (`toggleElementSelection` in select or comment mode, `toggleAreaSelection`, `setElementComments` for the pinned notes), and sends the element, the notes, a screenshot or the console to `_gemini.browser.addToPrompt`, which builds the attachments (`src/acp/pageContext.ts`) and adds them to the composer of the page's agent, else of the chat in front. The editor-scoped `geminiBrowserElementSelection` key marks a selection as Gemini's; upstream's chat integration (`browserEditorChatFeatures.ts`, one `GEMINI-FORK` check) ignores selections while Copilot's chat is off or the selection is Gemini's. Gemini's keybindings take upstream's (Cmd+Shift+C, Cmd+Alt+C) only while Copilot's chat is off.
- **Keep awake.** On macOS, while any prompt runs on the shared agent process (`AgentRuntime.onDidBecomeBusy` and `onDidBecomeIdle`), the extension runs `/usr/bin/caffeinate -i -w <extension host pid>` (`src/acp/keepAwake.ts`): it prevents idle sleep only, not display sleep, and exits on its own if the extension host dies, so it can never outlive GeminiCode. It is stopped when the last prompt ends, started again (up to three times per busy spell) if it exits on its own while a prompt still runs, and not tried again once it fails to start; `gemini.keepAwake` turns it off.
- **First open.** A first launch opens on Agent Home: the window defaults leave out upstream's onboarding and startup editor, and the Get Started walkthrough opens only from **Gemini: Get Started**. The first time a workspace opens, `layoutDefaults.ts` reveals the Gemini side bar (the workbench would otherwise open on the Explorer). After that the workbench restores whatever the user arranged.
- **Persistence.** The list of workspaces and agents is kept in global state, and each agent's visible conversation (the last 300 items, long text cut to 20,000 characters) and changed files are saved as one JSON file per agent in the extension's global storage. On reopen, or after the process restarts, GeminiCode resumes the session with `session/load` when the CLI supports it. Otherwise it starts a fresh session and says so in the chat.

GeminiCode builds this pane on public extension APIs rather than upstream's Agents window (`src/vs/sessions`). That window only takes agents registered in core code, and it is the fastest-moving part of upstream. The domain names (workspace, agent session) follow upstream's, so the views can move onto it if it gains an extension API.

### Look

The extension contributes two colour themes (`extensions/gemini/themes/`): **GeminiCode Dark** and **GeminiCode Light**, which the `ThemeSettingDefaults` edit above makes the defaults directly. Each is a complete theme with its own token colours, so it needs no other theme; a `configurationDefaults` entry would let upstream's default theme show first. High contrast defaults stay upstream's. The window defaults (above) put the view icons at the top of the side bar, hide the secondary side bar, use pill editor tabs and the browser button in the title bar, and open no startup editor or empty-editor hint; the extension's `configurationDefaults` set JetBrains Mono as the editor font, the `geminicode-icons` file icons, localhost links opening in the browser, no breadcrumbs or minimap, and a slightly roomier editor. Users can change each one. The layout uses only native views and editor groups, so every part stays resizable. The webviews' stylesheets (`media/chat.css`, `media/panels.css` and the shared `media/menu.css`) name the theme's colours once, as `--gemini-*` variables, so they follow any theme; high contrast themes keep their own colours and borders. Chat text is 14px. The Gemini gradient is kept to the sparkle, the working bar on the composer's top edge and the focused composer's outline. `media/glass.css`, loaded last on every page, gives the webviews the same glass: cards and the composer with a lighter top edge, glass buttons and pills, and pop-ups (the **+**, model, branch and folder menus in `webview-src/menu.ts`, the `@` and `/` picker, usage, and the dialogs) opaque with a sheen and one shadow; nothing uses `backdrop-filter` or a mask (`test/themes/noBlur.test.ts` fails on one), and every animation is a `transform` or an `opacity`, paused while the view is hidden. Selections, menu highlights and quick-input focus are graphite greys rather than the accent in both themes, and the user's chat bubble mixes the editor's foreground into its background (7%) and border (15%). The **Make It Yours** page (`appearance.ts`) marks the theme the window shows: with `window.autoDetectColorScheme` on it reads the preferred light or dark theme, and picking a theme turns auto-detect off so the pick holds. The model, branch and folder menus replace the system select menu and quick picks: the branch menu asks the extension for the folder's local branches (`listBranches`) and switches or creates one through the git extension's API (`switchBranch`).

### Team tools

`geminicode-tools` (`src/acp/teamToolsMcp.ts`) is GeminiCode's third MCP server. All four (the browser's, this one, a project's `geminicode-project` and the index's `geminicode-index`) are built on `localMcpServer.ts`: Streamable HTTP with plain JSON replies on `127.0.0.1`, one URL and HMAC bearer token per route, a JSON-RPC error for a request that fails and an error result the model can read for a tool that throws. The browser's and the team tools' routes are agents, with slots for spare sessions that are bound to the agent that takes the session (at most eight unbound slots are kept), and an agent's slots are dropped when it is removed, after which they answer 404. `TeamConnections` (`src/host/teamConnections.ts`) owns it and gives it to every session once any tool is connected. The connectors call each tool from the user's machine, so the VPN, proxy and certificates of the Mac apply: Jira Cloud REST v3 (`jira.ts`, email plus API token), GitLab REST v4 (`gitlab.ts`, `PRIVATE-TOKEN`), the SonarQube Web API (`sonar.ts`, bearer token), the user's Snyk CLI (`snyk.ts`, JSON and SARIF output) and the Figma desktop app's Dev Mode MCP server on `127.0.0.1:3845` (`figma.ts`, a small MCP client). `teamHttp.ts` gives every call an 8-second timeout and turns failures into a reason the user can act on (no answer: check the VPN; 401: replace the token). Tokens are in SecretStorage only; agents never see them. Tool results are trimmed text (`teamTools.ts`), never raw JSON, and the server lists tools only for connected tools, so a user with nothing connected pays nothing in prompt size. Reading tools are answered at once (`TeamConnections.instantAnswer`, the same hook projects use); the write tools always reach the permission card, and the confirm class among them (`teamConfirmTools`: a ticket's status, a time log, a new merge request, a merge, plus the same actions in a team's own `jira` and `gitlab` MCP servers) goes through `PermissionBroker.confirmOnly`, which drops every option but Allow once and Reject and skips the instant answers, because the CLI applies "Allow for this session" to all of a server's tools. Tool results that carry other people's text are wrapped in an `<external>` tag (`external()` in `teamTools.ts`), which the server's instructions tell the model to read as data. Every write, by an agent or from a page, goes through the audit log (`src/acp/auditLog.ts`, one JSON line per record in a file per day under global storage, never rewritten): an intent before the call, a result with the id the tool gave back after it, or the failure. An intent with no result is a write that was running when the app quit; **Open Audit Log** (`src/host/auditPage.ts`, a webview page over the same files) highlights those, Home lists them under Unfinished, and the status bar counts the day's writes (`auditStatusBar.ts`). **Record Performance Trace** (`src/host/traceCommand.ts`, `src/acp/traceRecording.ts`) restarts the agent once with the CLI's OpenTelemetry export going to a file in the home folder, prompts off. While it records, every turn's end gets a readout in the chat of where the time went, hop by hop against a budget for each hop (`turnReadout`: the fork's own hops from what the chat controller measured, the model's and the tools' from the CLI's file), and Stop reads the whole file back into a table of each turn's routing call, model calls, tool calls and cached tokens. The CLI writes its records as JSON objects back to back, not one per line, which `parseTraceFile` handles. Team defaults come from `.gemini/geminicode-tools.json` (`teamDefaults.ts`). Once the user takes over a repository's own Jira and GitLab servers (`src/host/teamTakeover.ts`), `TeamConnections` sets them up as children (`src/acp/teamContainers.ts`: pinned images, `docker run -i` with the tokens only in the child's environment, a curated tool list) through a small stdio MCP client (`src/acp/mcpStdio.ts`). Jira's and GitLab's are warmed when an agent's session opens, the others start on their first call, and each stops when idle. A call waits at most 8 seconds for a start under way, which goes on without it, and after a failed start calls skip the child for 5 minutes, so neither a container starting nor one that can't start holds up an agent's turn. `runTeamTool` sends the calls that map one to one through them and the rest, or everything when a child can't start, through the in-process connectors. **Run Benchmark** (`src/host/benchmarkCommand.ts`) and `scripts/bench-run.mts` share `src/acp/benchmark.ts`, which the command loads only when it runs. The pilot's counters (`src/acp/pilotLog.ts`) go nowhere unless `gemini.pilot.record` is on: `recordPilot` calls in the chat, the review, the team requests and writes reach a sink that `src/host/pilot.ts` sets, which appends a file per day, and **Export Pilot Data** writes them with the audit log to `~/geminicode-pilot/`.

### Workspace index

An index of each folder agents work in, and of documentation the user attaches, served to sessions by GeminiCode's fourth MCP server, `geminicode-index` (ADR 0010; the user's view is [the guide](guide/workspace-index.md)).

- **Where it runs.** `src/acp/index/indexer.ts` runs in its own process (`src/indexer.ts`, bundled to `dist/indexer.js`, never loaded in the extension host), forked by `IndexClient` with the app's own Node on the first request, at the lowest priority it sets itself, and stopped after ten idle minutes. A crash restarts it with a growing delay, three times at most. `WorkspaceIndex` (`src/host/workspaceIndex.ts`) owns the client and the server; on a restart it opens again the folders this window keeps current.
- **Storage and isolation.** One SQLite file per folder (`node:sqlite`), `~/.geminicode/index/code/<sha256 of the real path>/index.db`, in WAL mode and written in short transactions (`indexStore.ts`). A lock file with its pid (`indexLock.ts`) lets one window write; others read and take over when it goes. A file SQLite can't open or reports damaged, or from another schema, is moved aside and rebuilt; queries meanwhile answer from live search. An agent's worktree gets its own file, copied from its workspace's with `VACUUM INTO` and then reconciled, and removed with the worktree. Indexes no window used for 30 days are deleted.
- **What is indexed.** `git ls-files` (cached and untracked, not ignored) or a bounded walk (`inventory.ts`), less `.geminiignore`, `gemini.index.exclude`, `secretPathReason`'s files, binaries, lock files, minified code and files over `gemini.index.maxFileSizeKb`; `gemini.index.include` forces files back in, except secrets and binary content (`SkipRules`), and a file stored as left out is read again once it is included. `parse.ts` finds definitions with per-language line patterns (`languages.ts`), cuts chunks at top-level definitions (and at members of long classes), and keeps relative imports, resolved to files (`resolve.ts`). Chunk text is stored compressed. `cochange.ts` counts files changed together in the last 500 commits.
- **Keeping it current.** A reconcile compares size and mtime, then a content hash, so only changed files are parsed (`runReconcile`). Folders in the window get a file watcher each, batched a second after the last event, and a watch on HEAD and the branch refs (`indexWatchers.ts`); more than 300 changed paths at once reconcile instead. A worktree outside the window gets the agent's completed edits as they happen and a reconcile when each turn ends.
- **The tools.** `IndexMcpServer` (`src/acp/indexMcp.ts`) binds each agent's route and token to the folder it works in, and a spare session's slot to its folder, so no token reaches another folder's index. `code_search` runs BM25 over the chunks, names and paths weighted above body text, with the chunk defining a queried name first (`query.ts`); `find_symbol`, `related_files` and `repo_map` read the symbols, imports and co-change tables; results are capped at 8,000 characters (`format.ts`). While a folder's first build runs, `code_search` and `find_symbol` answer from the app's ripgrep and say so. The server's instructions carry the folder's outline (`repoMap.ts`), fetched when a session is prepared. It is one of `ownServers`, so `--allowed-mcp-server-names` always includes it.
- **Docs.** `DocsSources` (`src/host/docsSources.ts`) keeps the sources and the folders each is attached to in `~/.geminicode/index/docs/sources.json`, and fetches in the extension host (`src/acp/docs/crawler.ts`): `llms-full.txt`, `llms.txt`, the sitemap, then links under the address, within robots.txt, a page limit and conditional requests. The indexer converts HTML to Markdown (`htmlToMarkdown.ts`), cuts it by heading and stores each source once (`docsLibrary.ts`). Due sources refresh in the background; a lock beside the stores lets one window fetch a source at a time. A worktree's agent sees its workspace's docs.
- **Pages.** The Index page (`src/host/indexPage.ts`, `webview-src/indexPage.ts`) opens as a tab in the active group from Home, the Agents pane's workspace menu or **Gemini: Manage Index**; Home shows a drum icon beside the workspace pill (full, half or empty; whether a folder has an index is read from the index file, so Home never starts the indexer); the Files Left Out popup groups the left-out files by reason and adds files to `gemini.index.include`; the status bar shows **Indexing N%** only while a build of 50 files or more runs (`indexStatusBar.ts`). Suggested docs come from the folder's manifests and a list that ships with the extension (`src/acp/docs/suggest.ts`). Enhance prompt gets the folder's outline and the files the index finds for the draft, when it answers within 400 ms, and @-mentions outside the window list files from the index.
- **Getting the model to use it.** The chat sends `indexHint` with a session's first prompt once the folder's index is built (never shown in the chat), and search results rank tests below the code they test unless the query asks for tests, and say they are complete, so the model reads what they point to instead of checking with `grep_search`. Measurements are in [FINDINGS.md](FINDINGS.md#workspace-index).

### Context per model call

Project Helpers measures what every model call carries in the workspace (`src/acp/contextCost.ts`, `src/host/contextCostProbe.ts`): one "reply OK" prompt on the lightest Flash model per variant, each in a CLI started as agents are (`getAgentCommand` with an explicit `--allowed-mcp-server-names`): every server and GeminiCode's own (the total), none (the CLI and context files), an empty untrusted folder (the CLI alone), each server alone, and GeminiCode's servers alone. Each part is the difference between two variants. It runs only on request, the result is kept in global state per folder, and each server's share shows beside its switch, with advice for heavy parts. Memory files show a size estimate including the files they import with `@`.

## Gemini CLI management

GeminiCode's copies of the CLI get the app's ripgrep in `bundle/vendor/ripgrep/` (`cliRipgrep.ts`): the bundled copy when it is built, installed copies at launch. Without it the CLI's `grep_search` falls back to `git grep`. A CLI the user chose is left alone.


GeminiCode picks the CLI to run in this order:

1. The `gemini.cliPath` setting.
2. A copy installed from GeminiCode, from `<globalStorage>/gemini-cli/<version>/`. It uses `gemini.cli.version` if set, or else the newest installed copy.
3. The copy bundled with the app, in `extensions/gemini/cli/<version>/`, laid out the same way. Without a pinned version, a bundled copy newer than every installed one wins, so an app update is not held back by an older install. A pinned version that is neither installed nor bundled runs the bundled copy and offers to install the pinned one.
4. `gemini` on `PATH`.

The bundled version and its npm SHA-512 are pinned in `extensions/gemini/package.json` (`bundledCli`). `npm run bundle-cli` in `extensions/gemini` downloads it with `npm pack`, refuses a mismatched checksum, and unpacks `bundle/`, `package.json` and `LICENSE` into `cli/`, which git ignores. The release build runs it before packaging. The CLI is plain JavaScript with no native modules, so it needs nothing extra for macOS signing. Raise the pin only to a version the real-CLI tests pass on.

**Install Latest Gemini CLI** downloads the release from the npm registry, checks its SHA-512 checksum, and unpacks only `bundle/` and `package.json`. **Install or Change Gemini CLI Version...** lists the last 30 releases and pins the one picked in `gemini.cli.version` (unless policy locks it). Switching versions restarts the agent once no agent is working, and GeminiCode keeps only the installed copy in use (and a pinned one), so copies older than what runs, the bundled CLI included, are deleted. Once a day, after the agent is ready, it checks for a newer release and offers **Install**, **Skip This Version** or **Don't Check Again**; it never installs without a click, and skips the check when a version or path is pinned. A CLI older than `MIN_CLI_VERSION` (0.64.0) gets a warning, and the version list leaves those releases out.

## GeminiCode updates

GeminiCode does not update itself. Upstream's updater needs a server that answers per build, and a static GitHub Pages site cannot, so `product.json` has no `updateUrl`. Instead, a minute after start and then at most once a day across windows, `AppUpdateNotice` reads `latest.json` next to the download page (`geminiCodeDownloadUrl` in `product.json`). When it names a release newer than `geminiCodeVersion`, a notification says so, with **Download** (the page) and **Release Notes**. Only `https` links are opened. Dev builds, which have no `geminiCodeVersion`, never check, and admins can turn the check off with `GeminiCodeCheckForUpdates`. Full auto-update can come later with a small update server. See [RELEASING.md](RELEASING.md) for how releases and the page are built.

## Security model

ACP does **not** sandbox the agent. The CLI routes only its `read_file`, `write_file` and `edit` tools through the client's file requests. Its shell, `grep`, `glob` and `ls` tools run inside the CLI process with the user's permissions. What keeps the user in control:

1. **Approval modes.** In **Default** mode the CLI asks permission before every mutating tool. **Auto Edit** and **YOLO** skip some or all of those questions. Admins can remove either mode, and YOLO is off by default.
2. **Admin policy passed to the CLI.** GeminiCode writes a policy file and passes it with `--admin-policy`. When a mode is turned off, the CLI itself keeps asking in that mode. When shell access is off, the CLI removes its shell tool. The commands that print the environment (`env`, `printenv`, and `set` or `export` alone) are refused, even inside a longer command, unless `gemini.tools.denyEnvironmentCommands` is off. The confirm class (merge, open a merge request, move a ticket, log time, and the same actions in a team's `jira` and `gitlab` servers) asks in every mode, YOLO included; its rules name each tool as the model calls it (`mcp_<server>_<tool>`), because the CLI gives the policy check no server name for servers a session brings. In YOLO the chat still answers other requests itself, never those. With `gemini.mcp.allowedServers` set, GeminiCode also passes `--allowed-mcp-server-names` with that list and its own three servers, which outranks `mcp.allowed` in any settings file. Without it, when the settings files' `mcp.allowed` leaves out any of GeminiCode's servers, GeminiCode passes the flag with that allowlist plus its servers, less anything in `mcp.excluded` (`allowlistWith` in `projectToolsCheck.ts`), so users never add them by hand. A system policy directory on the machine overrides this file. `test/acp/realAgentPolicy.test.ts` checks all of it against the bundled CLI.
3. **Folder trust.** The CLI refuses Auto Edit and YOLO in a folder it does not trust. GeminiCode asks the user before adding the folder to the CLI's trusted list. A project needs its agents' folders trusted too, since the CLI loads no MCP servers in an untrusted folder; GeminiCode asks before trusting them, and never when `security.folderTrust.enabled` is off.
4. **No silent changes.** The IDE never changes the approval mode on the user's behalf.
5. **File requests stay in the folder.** The CLI's file tools go through the IDE, which refuses paths outside the agent's folder, secret files and git-ignored reads, following symbolic links to their real target. Session approvals of shell commands never cover a program that runs another program or code it is given (Permissions, above).

6. **Team tools ask for every write.** Write tools always reach a permission card with the exact text, and the confirm class (Team tools, above) offers only Allow once and Reject, in every mode. Every write, by an agent or a page, is in the audit log with its intent, its result and who answered.
7. **Other people's text is marked as data.** Tool results that carry text from Jira, GitLab, Figma or a page are wrapped in `<external … trust="untrusted">`, and the servers' instructions tell the model to read it as data, never as instructions.
8. **Tokens stay out of the agent's reach.** Team tool tokens are in the keychain (SecretStorage), never in settings or the agent's environment; taking over a repository's own Jira and GitLab servers moves their tokens out of the shell environment, and the environment commands are refused (2, above).
9. **Sites ask first.** In the browser, an agent opens other origins only after asking, per agent and site, and `gemini.browser.allowedOrigins` can pin them; the CLI's `web_fetch` refuses private hosts.

Reads through the CLI's own shell, `grep`, `glob` and `ls` are not covered by 5. Real containment needs the CLI's own `--sandbox` (Docker or Podman). It is not the default, because it would require a container runtime on every machine.

## Restarts

GeminiCode runs only on the Mac, with no server ([ADR 0009](adr/0009-desktop-only.md)): when it quits or the Mac restarts, the agent process, the local MCP servers and the team servers' children end, and nothing runs until a window opens again. Two rules follow: every flow that spans a model turn or a remote write can be picked up from a record on disk, and a restart never answers a question the user did not answer.

| State | Kept in | After a restart |
| --- | --- | --- |
| Agents, workspaces, projects and threads | global state | the same list and cards |
| Each conversation | one JSON file per agent in global storage, and the CLI's own chat file | shown at once; the session reopens with `session/load` |
| Undo and Rewind checkpoints | `<globalStorage>/checkpoints/<agent>.json`, written when a turn ends | up to the last finished turn |
| A turn that was running | the agent process | lost; the chat shows that it was cut off, with Retry the Turn and Keep and Continue |
| Permission cards and "Allow for this session" approvals | memory | gone: the next request asks again |
| An open team flow (Open Merge Request, Move Ticket, Review) | a record in `<globalStorage>/flows/`, with what the user typed and ticked | Home's Unfinished card offers Reopen from the same inputs, or Discard |
| A write that was in flight | its intent in the audit log, with no result | Home's Unfinished card lists it, with Open Audit Log and Mark as Checked; nothing is redone on its own |
| Home's team data | a snapshot in global state | shown at once, dimmed until it refreshes |
| Sign-in, team tokens, worktrees, folder trust | the CLI's files, the keychain, `~/.geminicode/`, `~/.gemini/trustedFolders.json` | as they were |
| The spare session and the team servers' children | memory and child processes | opened or started again when first needed |

## Direct requests

Inline edit and commit messages don't need a whole agent turn, so they skip the agent and send one request to a fast model (`gemini.inlineEdit.model`; by default the newest Flash model the installed CLI names, falling back to the previous one for accounts that can't use it yet) from `src/acp/directRequest.ts`. They use the sign-in the CLI saved, read only, and never change the CLI or its files:

- **Google sign-in** (`oauth-personal`): the access token in `~/.gemini/oauth_creds.json` calls the Gemini Code Assist service (`cloudcode-pa.googleapis.com`, the same one and the same license the CLI uses), billed to `gemini.projectId` or, without one, the project Code Assist reports for the user. An expired token is refreshed in memory with the CLI's own OAuth client, read from the installed CLI's bundle.
- **API key** (`gemini-api-key`): `GEMINI_API_KEY` calls the Gemini API.
- Vertex AI, and sign-ins kept in the system keychain, are not supported yet; the command says so.

Inline edit and Enhance prompt stream the answer (`:streamGenerateContent?alt=sse`): inline edit shows the rewrite's whole lines in the file above the lines it replaces, marked as added (`inlineEditPreview.ts`), then swaps in the clean rewrite as one undo step; Enhance prompt shows the rewrite in the read-only composer as it arrives. A request carries only the selection with up to 80 lines around it, or the diff (cut at 40,000 characters) and the last few commit subjects. `GeminiInlineEdit` turns both features off.

The **usage meter** (`usageMeter.ts`) makes the same `retrieveUserQuota` request the CLI makes, with the same project, at most every 10 minutes and only while the window is in front. The Gemini status bar item's tooltip lists each model's share of today's quota and when it resets, and the item shows the percentage once a model passes 80%. API key sign-ins have no quota to read, so it shows nothing. `GeminiUsageMeter` turns it off.

**Enhance prompt** (`promptEnhancer.ts`, `webview-src/enhance.ts`) is just as small a job, and is a direct request too (`QuickEdits.enhancePrompt`), on the inline edit model and under the same setting and `GeminiInlineEdit` policy. Direct requests carry the CLI's User-Agent, `user_prompt_id` and `session_id`, as the CLI's own requests do; on a real account they answer in 2.8 s at the median, against 4.8 s through the CLI ([FINDINGS.md](FINDINGS.md#prompt-enhancement-direct-requests-or-the-cli)). When direct requests are off, cannot use the sign-in, or fail (for five minutes after a failure), the CLI makes the rewrite: each in a fresh session on the shared agent process, in an empty folder (`<globalStorage>/enhance`), so earlier rewrites never leak into it, the CLI adds no folder context and the sessions stay out of the project's chat history. That session is put in Plan mode and on the first Flash-Lite (else Flash) model the agent offers, and only text sent during its prompt counts as the reply (gemini-cli sends a mode change as message text). While direct requests fail, the next session is opened ahead of the click. The draft goes with the names of its attachments, the chat's last six messages, the folder, branch, open file and mode, never file contents. The reply is cleaned (`cleanEnhancedPrompt`) and replaces the draft as an edit, so Undo brings it back. CLI sessions are not turns, so they never hold back a restart.

**Review My Changes** (`reviewPrompt.ts`, `AgentsView.reviewChanges`) starts an ordinary agent whose session opens in Plan mode (`setModeOnNextSession('plan')`), so the CLI itself refuses edits. The `git diff HEAD` (cut at 100,000 characters) goes as a `uncommitted.diff` document attachment, which keeps the chat bubble short and reaches the model as an embedded resource.

The **Project Helpers** page (`settingsPage.ts`, `projectSettings.ts`, `skills.ts`, `hooks.ts`, `cliCommands.ts`, `memory.ts`) edits the CLI's own files rather than keeping settings of its own: `mcpServers` in the personal and workspace `settings.json` (read as JSON with comments, and only rewritten when they have none), `mcp-server-enablement.json` keyed by the lowercased server name as gemini-cli's `McpServerEnablementManager` writes it, and the `context.fileName` rules files. Startup failures come from the same debug-log reader as the warnings. The page reads the files only when it is shown or changed, and never starts the CLI by itself: it asks the CLI only when the agent process is already running (on open, when the process becomes ready, after a change) or when the user presses **Refresh**.

Skills are read as the CLI reads them (`SKILL.md` and `*/SKILL.md` under the user's and project's `.gemini/skills` and `.agents/skills`, name and description from the front matter) and cached per folder until a `SKILL.md` changes (the watcher covers `SKILL.md` and `*/SKILL.md`, as the loader reads both); a project's skills are offered, in the `/` menu and on the page, only in a trusted workspace (`vscode.workspace.isTrusted`), since the CLI loads them only in trusted folders; picking one from the `/` menu sends a prompt asking the agent to load it with its `activate_skill` tool. Hooks are the `hooks` entries of the settings files, and a hook's switch edits `hooksConfig.disabled` in the file that defines it; because the CLI merges the disabled lists, switching on a project hook also removes it from the personal list. Extensions and memory come from the CLI itself: `/extensions list` (JSON) and `/memory list` run one after the other in one hidden session on the shared agent process (`runCliCommands`), which the CLI answers without the model, and enable and disable go the same way. A command is sent only when the session's `available_commands_update` lists it (otherwise it would reach the model as a prompt), a command that does not answer in time is cancelled, and the session is closed afterwards when the CLI advertises `sessionCapabilities.close`. Install, update and uninstall run `gemini extensions …` in a terminal instead, because the installer asks for consent on standard input, which over ACP is the protocol stream. Settings an extension resolved, which can hold keys, are never read. A skill's switch edits `skills.disabled` in the settings file of its scope (merged like `hooksConfig.disabled`, case-insensitive), and the `/` menu leaves out skills it lists; the skill cache also watches both settings files. **Sign In** on a remote MCP server runs `gemini -i "/mcp auth <name>"` in a terminal, since neither ACP nor the `gemini mcp` subcommands can run the OAuth flow; the CLI stores the tokens where every agent reads them. **Gemini CLI settings** (`src/acp/cliPreferences.ts`) read and write four keys of the user's `settings.json` through `updateSettingsFile`, which leaves a file with comments alone.

Team commands with `@{path}` or `!{command}` are expanded by `src/acp/teamCommandExpansion.ts` in one pass over the template, unlike the CLI, which runs its shell step over injected file text too: file text and command output are never searched again. `src/host/teamCommandHost.ts` reads a file only through `checkFileAccess` (workspace folders and the agent's folder, no secrets, nothing git ignores), refuses folders and files over 256 KB, and runs commands only when `gemini.tools.allowShell` is on and the user confirms the full list in a modal; they run with `shell: true` in the agent's folder, stop after 60 s, and keep 100,000 characters of output.

**Build This Plan** appears on the latest turn end when the session's mode is `plan` and the agent offers `default`; it sets the mode with `session/set_mode` and sends a short prompt. The status bar menu's **Report an Issue...** opens `reportIssueUrl` from product.json with the GeminiCode, VS Code, CLI and OS versions in the body (`src/acp/helpLinks.ts`), never an account, project or path.

## Sign-in and errors

- **Sign-in is delegated.** The CLI owns OAuth. GeminiCode calls `authenticate("oauth-personal")` only when `session/new` reports that sign-in is required, because the call rewrites `security.auth.selectedType` in the user's `~/.gemini/settings.json`.
- **Terminal fallback.** Some steps cannot finish over ACP: account validation, and a sign-in on a machine with no browser. For these, **Complete Setup in Terminal** runs the interactive `gemini` with the same environment, and GeminiCode restarts the agent when the terminal closes.
- **Errors are strings.** The CLI turns every setup failure into JSON-RPC error `-32000` with a message string; other failures arrive as a generic internal error with the CLI's message in `data.details`. `classifyAgentError()` matches those strings against a small table of known patterns (sign-in required or failed, project ID missing or numeric, untrusted folder), each with a test fixture. An unknown message is shown as it is.
- **Project ID.** GeminiCode resolves the Google Cloud project from the workspace setting, then the user setting, then the organisation default, then the `GOOGLE_CLOUD_QUOTA_PROJECT`, `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_PROJECT_ID` environment variables. It refuses to start the CLI with a project number, and only logs a warning for an ID that looks malformed.

## Upstream's own AI

The window defaults set `chat.disableAIFeatures` (above). That hides upstream's chat view, Copilot status item and inline chat. One `GEMINI-FORK` filter also keeps upstream's Chat commands out of the Command Palette. `product.json` still carries upstream's `defaultChatAgent`, because removing it would touch about 45 upstream files.

## Design rules

1. Discover model and mode IDs from the agent; never hardcode them.
2. Entitlement comes from the server, never from the client.
3. The CLI is a swappable runtime: any supported version, from any of the four sources.
4. Feature-detect and degrade. Hide a control the agent does not support, and render unknown update kinds generically.
5. Keep the wire-to-UI adapter thin (`sessionUpdates.ts`).
6. `extensions/gemini/src/acp` never imports `vscode`. ESLint enforces this.
7. Edit upstream files only at registration points, and mark each edit `GEMINI-FORK`.
8. Never patch the Gemini CLI. Speed comes from GeminiCode's own code: process reuse, prewarming, batching and caching.
