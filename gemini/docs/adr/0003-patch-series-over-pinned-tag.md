# ADR 0003: Upstream edits are a patch series over a pinned release tag

**Status:** accepted; `gemini/upstream.json`, `gemini/patches/`, `gemini/scripts/upstream-series.sh` and `gemini-upstream.yml` carry it out.

## Context

The fork merges upstream release tags three-way. The set of upstream files it edits is small (about 40 code and config files plus icons). Without a written series, each move would be a manual checklist from the `GEMINI-FORK` markers, which JSON files and icons cannot carry, and nothing would move the base or the Gemini CLI pin.

## Decision

- `gemini/upstream.json` pins the upstream release tag.
- Every edit to a file outside the fork-owned paths is kept as a patch in `gemini/patches/`, regenerated by `git format-patch`; a hygiene check fails when the series is stale.
- `gemini-upstream.yml` applies the series to the next `1.N.0` (and `1.N.x`) tag, copies the fork-only paths, runs the full compile, hygiene and extension tests, bumps `bundledCli` to the newest `@google/gemini-cli` with its integrity, runs the real-CLI tests against that exact version, and opens one PR.
- Branch protection requires the Gemini CI jobs and the upstream job; nothing merges with either red.
- History is not rewritten: existing clones keep working.
- Upstream's GitHub automation (its workflows and Dependabot config) is not part of the fork: the repository never goes back upstream, so `apply` and `prune` remove it and `check` fails while any of it is there.

## Consequences

- A conflict stops in CI with the patch name, not in a developer's merge.
- Reducing the number of patches becomes a visible metric.

## Evidence

The move from 1.141.0 to 1.142.0: 72 of the 74 patches applied cleanly, two needed a hand merge in files the fork edits at one point each, and the series stayed at 74 patches. CI's `Patch series matches HEAD` step checks the series on every pull request.
